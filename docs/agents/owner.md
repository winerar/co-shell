# Владелец и его предпочтения

Стабильные факты о проекте и о том, как владелец хочет работать. Меняются редко.

## Контекст продукта
- Приложение **только для своей семьи**, пользователей 2 (может стать больше, но немного).
- Оба телефона — **Android**. iPhone может появиться → держим готовность к KMP (`kmp-readiness.md`).
- Архитектура должна быть **бесплатной и надёжной**: никаких платных тарифов и своих серверов.
- Семья живёт в **Аргентине** (траты в ARS, USD), доход в **AMD**, есть счета в RUB.
  Важно для этапа 2 (доступность Firebase) и этапа 3 (источник курсов должен знать ARS и AMD).
- Частый случай: **оплата USDT-картой покупок в песо** (чек в ARS, списано USDT) — ввод в двух валютах
  важнее остальной мультивалютности. Курс песо — **официальный** (blue/MEP не нужен).
- **Много валют**; основную валюту отчётов можно менять, можно смотреть в нескольких сразу.
- **Не публикуем** в Google Play/RuStore. Установка APK + самообновление из приложения.
- Сейчас семья пользуется **Wallet (BudgetBakers)** → нужен импорт истории (ROADMAP этап 5).
- Название: co-shell ≈ «кошел(ёк)» / «общий кошелёк».

## Как работать с владельцем
- Общение — **на русском**, кратко, с рекомендацией, а не только списком вариантов.
- Принятые решения не переобсуждать без новой причины.
- **Задачи для владельца — всегда на доску** (2026-11-11): задача `type:owner` + `status:needs-owner` с пошаговой
  инструкцией, прямыми ссылками и готовым кодом для вставки прямо в задаче (правило — `tasks.md`).
- **Предупреждать, когда сессия разрослась** и токены тратятся быстро, — владелец начнёт новую.
- **В конце каждой сессии** сохранять состояние в репозиторий и **самому создавать PR** в `dev`;
  в `main` (= выкатка на телефоны) — **только по команде «релиз»** (`workflow.md`, «Git»).
- Код — **разбит на небольшие логические файлы** с понятной структурой, удобной для изучения
  человеком и агентом (правила — `project-structure.md` §«Файлы»).
- Владелец **не знает Kotlin**: объяснять результат словами, без разбора кода. Где возможно — делать
  **универсальные переиспользуемые компоненты** вместо копий (`project-structure.md` §«Переиспользование»).
- Приложение должно быть **лёгким, экономным к памяти, быстрым и плавным** (анимации без рывков
  на экранах 90/120 Гц) — правила в `performance.md`.
- В будущем — **своя дизайн-система**, на которую переезжают все экраны (ROADMAP §«Дизайн-система»).
- **Перед любыми визуальными изменениями — сначала визуальные примеры** (макет, варианты), код — только
  после «ок» владельца (2026-11-10; правило — `workflow.md` §«Визуальные изменения»).
- Держать `AGENTS.md` и `docs/agents/*` актуальными и небольшими (правила размера — в `AGENTS.md`).
- Макеты — **с длинными списками** (20–30+ элементов): работа с большим количеством должна быть удобной (2026-11-11).
- **Карточки-герои — с градиентом темы** и на макетах, и в коде (2026-11-12, #277).
- **Вкладки на всех экранах листаются свайпом**, не только нижние (2026-11-11).
