# Рабочий процесс

## Git
- Ветки: `dev` — интеграционная, `main` — только релизы. **Каждый мерж в `main` выкатывается на
  телефоны** (CI публикует обновление), поэтому в `main` прямо не коммитим и PR туда не делаем.
- Работа: рабочая ветка **создаётся от `origin/dev`** → PR в **`dev`** (CI проверяет, но ничего не публикует).
  Облачная сессия клонирует ветку по умолчанию (`main`) — поэтому первым делом
  `git fetch origin dev && git checkout -B <ветка> origin/dev` (своих коммитов ещё нет — безопасно).
- **PR и мерж автоматические.** Первый push ветки `claude/*`/`ccr-*` открывает **draft** PR в `dev`
  (`auto-pr.yml`) — сам PR не создавай. В конце сессии: дописать заголовок/описание (`Fixes #N`) и снять
  черновик — GitHub MCP `update_pull_request` (`draft: false`). После зелёного CI PR вливается сам
  (`automerge.yml`); метка `hold` — остановить. Конфликт с `dev` (бот напишет в PR) — `scripts/agent/sync-dev.sh`.
- Упал CI в PR — читай комментарий `<!-- ci-summary -->` (`pull_request_read` → комментарии), а не логи джоба.
- **Релиз — только по команде владельца** («релиз»): кнопка Actions → **Release** (`release.yml`, агенту —
  `actions_run_trigger` `run_workflow`, ref `main`). Она сама создаёт PR `dev` → `main` «Release: …», вливает
  и публикует. Перед этим в `docs/whats-new.md` должен быть новый верхний раздел для семьи (иначе стоп).
- Имя ветки — по смыслу: `<тип>/<тема>` латиницей через дефис, например `feature/transaction-entry`,
  `fix/balance-rounding`, `docs/session-rules`. Облачная сессия получает случайное имя
  (`claude/nice-hamilton-…`) — тогда смысл передаём заголовком PR и строкой в `STATUS.md`, а если
  владелец разрешил другое имя — создаём ветку `<тип>/<тема>` и работаем в ней.
- Коммит — одно логическое изменение, сборка и тесты зелёные.
- Сообщения коммитов — на английском, в повелительном наклонении: `Add MoneyParser`, `Fix ...`.
- Секреты (`google-services.json`, keystore, токены) никогда не коммитятся — см. `.gitignore`.

## Язык
- Общение с владельцем и документация в `docs/` — на русском.
- Код, комментарии, коммиты — на английском. Строки UI — русский, в ресурсах.

## Документация — часть изменения
| Изменилось | Обновить |
|---|---|
| Модули, пакеты, структура | `docs/agents/project-structure.md` |
| Команды сборки, версии SDK, CI | `docs/agents/build-and-test.md` |
| Архитектурное решение | `docs/ARCHITECTURE.md` + строка в «Принятые решения» |
| Завершён пункт плана | отметить `[x]` в `docs/ROADMAP.md` |
| Новое общее правило | подходящий файл в `docs/agents/` (или новый + ссылка в `AGENTS.md`) |

Правила размера файлов — в `AGENTS.md`, раздел «Как поддерживать эти файлы».

## Сессии ИИ-агента и расход токенов
- Длинная сессия дорожает: каждый ответ заново читает всю историю. **Одна задача из `STATUS.md` —
  одна сессия.** После push и обновления `STATUS.md` предлагай владельцу новую сессию.
- Предупреждай, когда сессия разрослась (много больших файлов/логов в контексте).
- Перед сменой сессии всё нужное — в репозитории: код запушен, `STATUS.md`/`ROADMAP.md` обновлены.
- Сборка и тесты — `scripts/agent/check.sh` (`--quick` — только тесты), не голый `./gradlew` (шум прокси).
- Читай куски файлов (`sed -n`, `grep -n`), а не файлы целиком; режь вывод (`tail`, `head`, `-q`).
- Не перечитывай то, что уже есть в контексте; правки — точечные (`Edit`), а не перепечатка файла.

## Самоулучшение (агент делает сам, без отдельной команды)
- **Узнал** что-то неочевидное (замер, грабли, приём с инструментом) → строка в `notes.md`.
- **Рутина** повторилась второй раз (несколько команд подряд, разбор вывода) → скрипт в `scripts/agent/`
  с кратким выводом + строка в таблице `notes.md`. Скрипт — bash/python3 без новых зависимостей.
- **Ввёл практику** (новое ограничение, порядок действий) → правило в тематический файл `docs/agents/`.
- Проверка, которую можно автоматизировать, — в `session-end.sh` или CI, а не только текстом.

## Разбор отзывов (issue с меткой `feedback`)
- Отзывы из «Ещё → Обратная связь» приходят issue с меткой `feedback` (`docs/setup/feedback.md`).
- По команде владельца («разбери отзывы»): прочитать открытые `feedback`-issue (GitHub MCP
  `list_issues`, `labels: [feedback]`), сгруппировать, мелкие починить пачкой в одной ветке.
  Непонятное или крупное — вопрос владельцу / пункт в ROADMAP, не угадывать.
- В описании PR — `Fixes #N` на каждый issue: закроются при релизе (мерж в `main`).
  Пункт для семьи — в `docs/whats-new.md`.

## Начало сессии (обязательно)
Параллельные сессии работают в своих ветках, и `STATUS.md` в `main` может отставать.
Перед любой работой:
1. `scripts/agent/session-start.sh` — fetch, ветки с коммитами не в `dev` (коммиты + строка STATUS),
   перенос своей пустой ветки на `origin/dev`, шаги из STATUS. Затем прочитать `notes.md`.
2. Есть невлитые коммиты → прочитать `docs/STATUS.md` **из этой ветки** (`git show <ветка>:docs/STATUS.md`).
3. Рабочая ветка стоит на `origin/dev` (раздел «Git»); если нет — перенести на него.
4. Если задача уже сделана или начата в другой ветке — не дублировать: сообщить владельцу и
   предложить влить ту ветку (PR) или продолжить от неё.

## Конец сессии (обязательно)
Перед тем как завершить сессию или предложить новую:
1. Код закоммичен и запушен, CI зелёный (или в `STATUS.md` записано, что сломано).
2. `docs/STATUS.md` переписан: этап, что сделано, следующие шаги, открытые вопросы, строка о сессии.
   Раздел «Последняя сессия» — только последняя сессия, старые строки удалять.
3. `docs/ROADMAP.md` — отмечены `[x]` выполненные пункты. Есть заметное семье изменение —
   пункт в верхний раздел `docs/whats-new.md` (новый раздел с датой, если прошлый уже выпущен).
4. Новые решения → `docs/ARCHITECTURE.md`; новые предпочтения владельца → `docs/agents/owner.md`;
   новые правила → подходящий файл в `docs/agents/`.
5. `scripts/agent/session-end.sh` — без ✗. Снять черновик с PR в `dev` (раздел «Git») — дальше автомерж.
   В `main` — только по команде «релиз» (раздел «Git»).
6. Сообщить владельцу итог и как начать следующую сессию (окружение **co-shell**, первая фраза).
