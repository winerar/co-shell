# Архитектура co-shell

## 1. Исходные условия
- Приложение для одной семьи, **2 пользователя** (может стать больше, но не десятки).
- **Бесплатно** — никаких платных тарифов и своих серверов.
- **Надёжно** — данные не должны теряться, приложение работает без сети.
- **Много валют** — счета в разных валютах, отчёты в выбранной валюте (или сразу в нескольких),
  базовую валюту можно сменить в любой момент.
- **Без публикации** — установка APK напрямую, Google Play не нужен.

minSdk 26.

## 3. Почему Firebase Firestore
| Вариант | Бесплатно | Надёжность | Вердикт |
|---|---|---|---|
| **Firestore (Spark)** | да: 1 ГБ, 50k чтений / 20k записей в сутки — двоим хватит с запасом в сотни раз | инфраструктура Google, офлайн-кэш и realtime-обновления из коробки | ✅ выбран |
| Supabase Free | да | проект **ставится на паузу** после 7 дней без активности | ❌ |
| Свой сервер (Ktor/PocketBase) | нужен хостинг (или «вечно бесплатный» VPS без гарантий) | зависит от вас | ❌ |
| P2P / файл в облаке | да | конфликты и слияние придётся писать самим | ❌ |

Риски и как их закрываем:
- **Привязка к одному поставщику (vendor lock-in)** — сеть спрятана за интерфейсом `RemoteDataSource`,
  domain и UI про Firebase не знают. Room остаётся полноценной базой на устройстве.
- **Нет бесплатных серверных бэкапов** — делаем **резервные копии сами**: WorkManager раз в неделю
  выгружает JSON в выбранную папку (Google Drive / локально через Storage Access Framework),
  плюс ручной экспорт/импорт.
- **Доступность сервисов Google в регионе** — проверяем в начале этапа 2; если что-то не работает,
  меняем только реализацию `RemoteDataSource`.

**Безопасность:** в Firestore одна семья, правила доступа пускают только пользователей, чей uid
есть в списке участников семьи. Регистрация чужих людей ничего им не даёт.

## 4. Архитектурный стиль
Упрощённая Clean Architecture + MVVM, данные идут в одну сторону (UDF).

```
Compose screen ──events──▶ ViewModel ──▶ UseCase ──▶ Repository
       ▲                       │                       │
       └────── StateFlow ◀─────┘          Room (источник истины)
                                                       ▲ ▼
                                        SyncEngine ⇄ Firestore
```
- Экраны читают **только из Room**.
- Запись: сначала в Room с флагом `pendingSync`, затем `SyncEngine` отправляет в Firestore;
  изменения от второго пользователя приходят опросом (pull по серверному времени) и пишутся в Room (§10).
- Конфликты: побеждает последняя правка (last-write-wins) по времени правки на телефоне; удаления —
  через пометки-tombstones (`deleted = true`).
- ID генерирует клиент (UUID) — записи можно создавать без сети.

### Модули (стартуем компактно, дробим по мере роста)
```
:app                — точка входа, навигация, DI
:core:model         — Money, Currency, доменные сущности (KMP, чистый Kotlin)
:core:domain        — use cases, интерфейсы репозиториев, конвертация валют (KMP)
:core:data          — Room, репозитории, SyncEngine, Firestore, курсы валют (KMP: android + jvm для тестов)
:core:designsystem  — тема и общие компоненты
:feature:*          — экраны (transactions, accounts, categories, budgets, reports, settings, auth)
```

## 5. Модель данных
Служебные поля всех синхронизируемых сущностей: `id (UUID)`, `updatedAt`, `updatedBy`, `deleted`.

- **Family** — name, `reportCurrencies: List<CurrencyCode>` (первая — основная)
- **Member** — uid, displayName
- **Account** — name, **currency**, type (cash / card / deposit…), isShared, ownerMemberId?, initialBalanceMinor, archived
- **Category** — name, icon, color, type (expense / income), parentId?
- **Transaction**
  - type: expense / income / transfer
  - accountId, `amountMinor: Long` — **в валюте счёта**
  - для transfer: `toAccountId`, `toAmountMinor` — сумма зачисления в валюте второго счёта
    (обмен валюты = перевод между счетами в разных валютах, реальный курс сохраняется сам собой)
  - categoryId, date, note, authorMemberId
  - `originalAmountMinor?`, `originalCurrency?` — если платили в валюте, отличной от валюты счёта
    (например, рублёвой картой в евро): что было в чеке и что списали
  - `payee?` — получатель/магазин, `labels: List<String>` — метки (нужны и для импорта из Wallet)
  - `importSource?`, `importExternalId?` — откуда импортирована запись (повторный импорт не создаёт дублей)
- **Budget** — лимит («конверт»): categoryId (категория или папка), startMonth («с этого месяца», повторяется),
  `limitMinor`, **currency**, note?, rollover (перенос остатка), lastMonth? (снят «с месяца»)
- **ExchangeRate** — date, from, to, rate, origin: `DOWNLOADED` (кэш, не синхронизируется) или
  `MANUAL` (ручная правка курса, синхронизируется, имеет приоритет)

## 6. Мультивалютность
**Принцип: факты храним в исходной валюте, конвертируем только при показе.**

1. Каждая сумма хранится в своей валюте (валюта счёта / бюджета). Никакие данные не пересчитываются
   при смене базовой валюты — поэтому сменить её можно в любой момент, мгновенно и без потерь.
2. **Валюты отчётов** — список в настройках семьи. Главный экран и отчёты показывают итоги в основной
   валюте, при желании — параллельно в остальных (например, «₽ 120 000 · € 1 250»).
3. Конвертация — по курсу **на дату операции** (для трат и доходов) и по текущему курсу (для балансов
   счетов). Порядок поиска курса: ручной курс на дату или раньше (действует до следующего ручного) → кэш на дату →
   ближайшая предыдущая дата → кросс-курс через USD → ближайшая более поздняя дата (если раньше ничего нет).
4. **Источник курсов:** бесплатный публичный API без ключа
   (`fawazahmed0/exchange-api` через CDN: 150+ валют, включая RUB и крипту, есть история по датам);
   зеркало тех же файлов — Cloudflare Pages (`<дата>.currency-api.pages.dev`); резервный источник —
   open.er-api.com (без ключа, знает ARS и AMD, только последний курс, ссылка-атрибуция на экране «Ещё → Курсы валют»).
   Источники перебираются по порядку за `RatesProvider` (`core:domain/rates`).
   Курсы скачиваются раз в день через WorkManager (`RatesRefreshWorker` → `RefreshRatesUseCase`, только при
   сети) и хранятся локально, поэтому отчёты работают офлайн. За один запуск: последний курс (если на сегодня
   ещё нет) + история для дней операций без курса — от новых к старым, не больше 30 дней (импорт Wallet
   растянется на несколько дней), не раньше 2024-03-02 (начало истории currency-api); 3 ошибки подряд — стоп.
   Экран «Ещё → Курсы валют» показывает курсы на сегодня, дату и источник последней загрузки, кнопку
   «Обновить сейчас» (разовый `OneTimeWorkRequest` того же воркера) и ручные курсы (добавить, изменить, удалить).
5. **Точность:**
   - суммы — `Long` в минимальных единицах; число знаков после запятой берём из `java.util.Currency`
     (JPY — 0, EUR — 2, KWD — 3), для валют вне ISO 4217 — своя таблица;
   - курсы — свой точный десятичный тип `Rate` (не `java.math.BigDecimal`, без библиотек), в БД хранятся строкой,
     округление по правилу банкира (HALF_EVEN), и только при показе.
6. Бюджеты задаются в своей валюте; траты в других валютах пересчитываются в валюту бюджета по курсу на дату траты.

## 7. Распространение и самообновление
Без публикации в магазинах. Схема (включается секретами — `docs/setup/self-update.md`):

```
мерж dev → main (релиз) ─▶ CI: versionCode = номер запуска ─▶ подписанный release-APK
                                                                 │  scripts/make-update-files.py
                                                                 ▼
          публичный репозиторий co-shell-releases, релиз build-<N>: co-shell-<N>.apk + version.json
                                                     │
          приложение: …/releases/latest/download/version.json — при выходе на передний план, ≤ раз в сутки
                                                     ▼
                  «Доступна версия X» ─▶ загрузка ─▶ проверка SHA-256 ─▶ PackageInstaller
```

- Основной репозиторий приватный (там сведения о семье), а приватные релизы не скачать без токена,
  поэтому APK лежат в отдельном **публичном** `co-shell-releases` — только APK и `version.json`.
  CI пишет туда fine-grained токеном `RELEASES_TOKEN` (Contents: write только на этот репозиторий).
  Firebase Hosting отпал: на Spark запрещены исполняемые файлы (`.apk`).
- `version.json`: `versionCode`, `versionName`, `apk` (абсолютная ссылка на релиз `build-<N>`), `sha256`,
  `size`, `notes` (верхний раздел `docs/whats-new.md`). Разбор — `app/.../update/data/ReleaseManifest.kt`:
  только https, проверка формата хэша. GitHub отвечает редиректом на своё хранилище — `HttpURLConnection`
  идёт по нему сам.
- Решения — в `core:domain/update`: `CheckForUpdateUseCase` (автопроверка в сети ≤ раз в час, с экрана —
  всегда; найденная версия запоминается и предлагается при каждом запуске, пока не установлена, —
  в одном запуске каждая версия один раз), `WhatsNewUseCase` (перед установкой релиз запоминается, после перезапуска «Что нового» — один раз).
- Установка — `PackageInstaller` (сессия), разрешение `REQUEST_INSTALL_PACKAGES`; результат —
  `InstallResultReceiver`. Пользователь один раз разрешает «установку из этого источника», дальше —
  один тап (на Android 12+ возможно и без подтверждения, если co-shell сам себя установил).
- Перед установкой проверяем SHA-256 скачанного файла; Android дополнительно проверяет, что подпись
  совпадает с установленной версией.
- Самообновляется только **release** (`app.coshell`); debug (`app.coshell.debug`, «co-shell debug»)
  по-прежнему уходит в Releases приватного репозитория. Переход debug → release — один раз через копию.
- **Ключ подписи** создаёт workflow `Create release key` (артефакт живёт сутки), хранится в GitHub Secrets
  **и** у владельца. Потеря ключа = переустановка с потерей локальных данных.
- Фоновой проверки через WorkManager нет: проверка при открытии приложения покрывает это.

## 8. Импорт из Wallet (BudgetBakers)
Сейчас семья ведёт бюджет в Wallet; историю нужно перенести в co-shell.

- **Источник:** экспорт записей из Wallet в CSV (веб-версия Wallet). Формат сверен на реальном
  файле 2026-11-08; синтетический образец — `docs/samples/wallet-export-sample.csv`
  (реальные выгрузки в публичный репозиторий не кладём).
- **Формат файла:** UTF-8, разделитель `;`, первая строка — заголовок, записи от новых к старым.

  | Колонка | Что там | Как используем |
  |---|---|---|
  | `account` | имя счёта Wallet | сопоставление счетов |
  | `category` | имя категории (у переводов — `TRANSFER`) | сопоставление категорий |
  | `currency` | валюта **записи** — обычно валюта счёта (у счёта «USDT» было `USD`), но бывает другая | валюта суммы |
  | `amount` | сумма со знаком, точка — разделитель (`-13.00`) | знак → расход/доход, модуль → `amountMinor` |
  | `ref_currency_amount` | та же сумма в базовой валюте Wallet (в образце — AMD) | исторический курс → `ManualRate` |
  | `type` | **локализованный** тип (`Gastos`/`Ingresos` в испанском UI) | не используем — берём знак `amount` |
  | `note` | заметка | `note` |
  | `date` | `yyyy-MM-dd HH:mm:ss`, локальное время **без часового пояса** | пояс выбирается в мастере (по умолчанию — телефона) |
  | `transfer` | `true`/`false` | склейка переводов |
  | `payee` | получатель (в образце всегда пусто) | `payee` |
  | `labels` | метка; у записи **всегда не больше одной** (подтвердил владелец) | `labels` = `[метка]` или пусто |
  | `envelope_id` | системный id категории Wallet, не зависит от языка (`20001` — перевод, `10000` — зарплата) | подсказка при сопоставлении |
  | `payment_type`, `payment_type_local`, `gps_*`, `warranty_in_month`, `custom_category` | служебное | игнорируем |

- **Особенности, найденные на реальном файле:**
  - Перевод = две строки с `transfer=true` и одинаковым `date` до секунды, суммы с разными знаками,
    `|ref_currency_amount|` совпадают; валюты могут различаться (USD +1500 ↔ AMD −539 810 — это обмен).
  - Бывают **непарные** переводы: одна строка без пары (перевод на счёт вне выгрузки или записи
    сделаны в разное время). В мастере: выбрать второй счёт или превратить в расход/доход.
  - Одно имя категории может встречаться с разными `envelope_id` (`Продукты` — 1000 и 1003):
    сопоставляем по имени, `envelope_id` — только подсказка.
- **Полная выгрузка владельца (2026-11-09, проверена разбором `core:domain`):** 1600 записей за
  2026-01-01…2026-11-08, **0 ошибок разбора**; 22 счёта, 7 валют (AED, AMD, ARS, EUR, GEL, RUB, USD),
  38 категорий, 17 меток, `payee` пуст везде, точных дублей строк нет. Базовая валюта Wallet — AMD.
  - **Запись в чужой валюте счёта:** у AMD-счёта есть перевод в RUB (−4675 RUB, `ref` −22 150,10 AMD).
    У счёта co-shell валюта одна → сумма в валюте счёта берётся из `ref_currency_amount`, если валюта
    счёта = базовая; иначе — пересчёт по курсу дня с подтверждением; исходная сумма → `originalAmount`
    (как «чек в другой валюте»), у перевода — вторая сумма. Валюта счёта — самая частая у его записей.
  - **Непарных переводов 51 из 230** (≈ 22 %), близких пар (±10 мин, ±3 %) среди них нет — значит,
    вторая сторона на счёте, которого нет в выгрузке (удалён/скрыт/не выбран в фильтре экспорта).
    Часто пачкой в одну минуту — владелец: «скорее всего» выравнивание балансов; удалённые счета — «возможно».
    История в Wallet начинается с 2026-01-01 (подтвердил владелец) — выгрузка полная.
  - **Начальных балансов в CSV нет** → баланс счёта после импорта ≠ Wallet. Решение — в мастере
    ввести «баланс в Wallet сейчас» и записать разницу в начальный баланс счёта (без лишних операций).
- **Разбор (сделан, 5а):** колонки ищутся по имени заголовка; битая строка → ошибка с номером строки,
  остальное читается (мастер покажет ошибки и спросит, импортировать ли прочитанное); незакрытая кавычка
  или нет обязательных колонок — файл целиком не читается. Суммы — строго `-13.00` (точка, без групп);
  лишние знаки после запятой допустимы только нулями (`-500000.00` у валюты без копеек).
  Пары переводов ищутся уже при разборе (`WalletTransferMatcher`) — для сводки и шага «Переводы».
- **Сопоставление (сделано, 5б, `core:domain/importer/wallet/`):** `WalletAccountMatcher` и
  `WalletCategoryMatcher` дают подсказки (слить по имени без учёта регистра, только та же валюта / тот же
  тип; иначе создать), мастер создаёт новые счета и категории и передаёт готовые id в
  `WalletImportDecisions`; `WalletImportBuilder` собирает операции и список проблем (нет решения, нужен
  курс, нулевая сумма) — ничего не угадывает. Непарный перевод по умолчанию — «корректировка».
  `importExternalId` — FNV-1a 64 от полей записи + номер среди одинаковых, считая **от старых** (новая
  выгрузка добавляет записи только с нового конца — id известных не меняются); у пары — от обоих id.
  Время записи переводится в `Instant` поясом, выбранным в мастере (пояс телефона → время как в Wallet).
- **Защита от дублей на уровне БД:** уникальный индекс `(import_source, import_external_id)`.
  Room `@Upsert` при конфликте по этому индексу **молча пропускает** запись, поэтому импортёр сам
  проверяет `importExternalId` до сохранения и показывает, сколько записей пропущено.
- **Где работает:** импорт идёт в приложении на телефоне (файл выбирается через системный диалог).
  Код разбора CSV и сопоставления — в чистом Kotlin (`core:domain`/отдельный модуль `core:importer`),
  покрыт тестами на образцах.
- **Мастер импорта:**
  1. разбор файла и сводка (сколько записей, период, валюты);
  2. сопоставление счетов и категорий Wallet → co-shell (создать новые или слить с существующими);
  3. переводы: в Wallet перевод — две записи (списание + зачисление), склеиваем их в один transfer
     с двумя суммами;
  4. предпросмотр и импорт одной транзакцией в Room → дальше обычная синхронизация.
  **Сделано (5в, 2026-11-10):** «Ещё → Импорт из Wallet» (`app/.../importer/wallet/`): файл → сводка → счета
  (+ «баланс в Wallet сейчас») → категории → переводы без пары (шаг скрыт, если их нет) → проверка → готово.
  `WalletImportPlanner` (чистый) строит запись и предпросмотр, `WalletImportUseCase` — чтение/сохранение,
  `ImportRepository` (`RoomImportRepository`, `ImportDao`) — одна транзакция. Перед записью — копия
  `PreImportBackup` (внутренняя папка + папка автокопий, если включена); не вышло — импорт не начинается.
- **Пакет импорта (схема v6):** у операций одной загрузки общий `importBatchId` (синкается и в бэкапе).
  «Отменить импорт» мягко удаляет операции пакета **и снимает с них `import_source/external_id`** — иначе
  уникальный индекс не дал бы повторно загрузить тот же файл. Счета/категории и сверка начального баланса
  при отмене остаются. Удалённая вручную импортная операция остаётся «известной» и не возвращается.
- **Без дублей:** у каждой записи `importSource = "wallet"` + `importExternalId` (хэш значимых полей),
  повторный импорт того же файла пропускает уже загруженное.
- **Корректировка баланса (сделано, 5б):** системные категории с постоянными id
  `system-adjustment-expense` / `system-adjustment-income` (`core:model` `SystemCategories`) — оба телефона
  создают одну и ту же строку, синк их сливает. Создаёт/восстанавливает `EnsureAdjustmentCategoriesUseCase`
  (его результат — `WalletImportDecisions.adjustmentCategories`). Операции в них меняют баланс, но **не траты
  и не доход**: `expenseTotals`/`incomeTotals`/`dailyExpenses` их пропускают (`Transaction.isBalanceAdjustment`),
  отчёты этапа 6 — тоже. Тип (расход/доход) у них не меняется; переименовать, архивировать можно.
- **Сверка балансов (сделано, 5б):** `WalletBalances.afterImport` — баланс каждого счёта после импорта
  (текущий + движения новых операций), `WalletBalances.reconcile` — разница с «балансом в Wallet сейчас»
  уходит в начальный баланс счёта.
- **Курсы из выгрузки — не сохраняем (на решении владельца):** план был писать курс из `ref_currency_amount`
  как `ManualRate`, но ручной курс по правилам `RateBook` действует **до следующего ручного** — последний
  курс Wallet заменил бы официальные скачанные курсы и для всех будущих дат. А официальная история и так
  скачивается на все дни операций (`RefreshRatesUseCase`, с 2024-03-02; история Wallet — с 2026-01-01).
- Бюджеты, плановые платежи и вложения Wallet в CSV, скорее всего, не попадают — переносим вручную.

## 10. Синхронизация и семья (этап 4)
**Без Firebase SDK** — REST-запросы через `HttpURLConnection`, как у отзывов: SDK Firestore + Auth
весят несколько МБ, тянут gRPC и Google Play Services, а нам их офлайн-кэш не нужен — источник истины
Room. REST-код лежит в `core:data` (commonMain) — пригоден для iOS (KMP).

**Вход:** Credential Manager («Войти через Google», `app/family/data/GoogleSignIn.kt`) → Google ID token →
Firebase Auth REST `accounts:signInWithIdp` → `AuthSession` (uid, email, токены) в приватных
SharedPreferences; ID-токен обновляется через `securetoken` за 5 минут до истечения (`AuthManager`).
Без входа приложение работает как раньше; локальные правки помечаются uid вошедшего (`WriteStamper`).

**Семья** — одна на проект: `families/main` {`ownerUid`, `memberUids`, `members`{uid → name, email}}.
Создать её может первый вошедший (правила разрешают только id `main`), дальше — только по приглашению
`invites/{gmail}` {`familyId`, `invitedBy`}: приглашённый с подтверждённым email добавляет в семью
только себя. Членство кэшируется в `sync_state` (`FamilyService`) — синк и имена работают офлайн.
При входе в семью со своими операциями: «Заменить» (копия в `files/backups/`, затем очистка таблиц)
или «Добавить в семью» (все строки снова `pending_sync`).

**Записи:** одна коллекция `families/main/records/{kind}_{id}`: `kind`, `id`, `updatedAt`, `updatedBy`,
`deleted`, `json` (сущность Room целиком, `SyncCodec`), `serverUpdatedAt` (= `REQUEST_TIME`).
Одна коллекция → один запрос на скачивание; пустой опрос стоит одно чтение.

**`SyncEngine.sync()`:** (1) pull — записи строго после курсора `(serverUpdatedAt, имя документа)` (`startAt … before=false`,
страницы по 500; время хранится как прислал сервер, с микросекундами), слияние в
транзакции Room: побеждает больший `updatedAt` (время правки на телефоне), при равенстве — больший
`updatedBy`; более новая локальная правка остаётся `pending`; курсор в `sync_state`.
(2) push — все `pending_sync` строки пачками ≤ 400 (`commit`); флаг снимается, только если строка не
менялась во время отправки (`WHERE updated_at = :sent`). Pull раньше push, чтобы старая офлайн-правка
не затёрла новую. Окно гонки между pull и push — секунды; для двоих приемлемо.
Удаление — tombstone `deleted = true`, удалять документы правила запрещают.
Запись неизвестного `kind` (версия новее) телефон пропускает, но курсор уходит дальше — поэтому `sync_state["pull_kinds"]`
хранит список понятых видов: после обновления, добавившего вид, первый pull читает всё заново (один раз).

**Когда:** пока приложение открыто — сразу при открытии и затем раз в минуту (`ForegroundSync`;
решение владельца 2026-11-11); правки второго телефона приходят сразу по «звонку», опрос — запасной путь.
Через 1 с после правки (`SyncScheduler.syncSoon`, WorkManager); в фоне — раз в час
(`SyncWorker`). Listen API у Firestore REST нет, поэтому мгновенность даёт «звонок».

**Звонок (мгновенный синк, пока приложение открыто):** отправив свои записи (`pushed > 0`), телефон пишет
`{at: серверное время, by: uid}` в `families/main/ping` Realtime Database по REST (`FamilyBell.ring`);
второй телефон держит поток SSE на этот узел (`FamilyBell.rings`, `UrlConnectionEventStream`, только
в foreground — вместе с `ForegroundSync`) и на чужой звонок сразу делает `sync()`. Задержка правки ≈ 2–3 с.
В звонке нет данных бюджета. Доступ — `firebase/database.rules.json`: `families/main/members/{uid}: true`;
список заполняют сами телефоны (`FamilyBell.register`, только добавление): первый участник вписывает себя,
пока список пуст, участники — остальных из списка семьи Firestore (второй участник получит доступ, когда
откроется телефон первого). Поток переподключается: после `auth_revoked` (ID-токен истёк, раз в час) сразу,
после ошибок — с паузой до 2 мин. Звонок — только ускорение: если RTDB не создана или недоступна,
синк идёт опросом. Адрес — переменная `FIREBASE_DATABASE_URL`, по умолчанию `<проект>-default-rtdb.firebaseio.com`.

**Квота Spark** (50k чтений/сутки): пустой опрос — 1 чтение; при открытом приложении ≈ 60–360
чтений/час на телефон (медленный/быстрый темп) + по чтению на каждую изменённую запись (свои
отправленные записи телефон тоже читает обратно — фильтр «не мои» потребовал бы составной индекс).
Пока в семье один участник, документ семьи перечитывается не чаще раза в минуту (`FamilyService`).
Записей — 20k/сутки: большой импорт может их исчерпать (#130). Тогда отправленные пакеты остаются
отправленными, остальное ждёт с флагом `pending_sync`, а отправка встаёт на паузу до сброса квоты
(полночь по Тихоокеанскому времени; `QuotaPause`, ключ `push_paused_until` в `sync_state`); получение
идёт дальше, баннер «Дневной лимит исчерпан» держится, пока очередь не уйдёт; `SyncWorker` не повторяет.

**Проверка:** `SyncEngineTest`/`FamilyServiceTest` (два телефона и поддельный сервер), `FamilyBellTest`,
`ServerSentEventsTest`; правила Firestore и RTDB — `firebase/rules-test` и сквозной `FirestoreEmulatorTest` в эмуляторе (`scripts/test-rules.sh --kotlin`).
