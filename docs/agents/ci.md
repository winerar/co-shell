# CI: проверки, мерж, релиз

Путь изменения: ветка агента → PR в `dev` (CI) → автослияние → CI на `dev` → кнопка релиза → PR `dev` → `main` → CI на `main`
публикует сборку. Цель — не делать одну и ту же работу дважды (#224). Сбой или потеря данных — хотфикс: ветка от `main` → PR в `main`
(CI + эмулятор параллельно) → автомерж → сборка → `main` вливается в `dev` (`hotfix.md`).

## Воркфлоу
- `ci.yml` — push в `main`/`dev`, PR (кроме черновиков: сборка на `ready_for_review`), вручную (Actions → «Сборка и тесты (CI)» → Run workflow).
  Gradle пропускается, если изменены только `docs/`, `*.md`, `scripts/agent/`.
- **Минуты Actions** (#251, #253): приватный репозиторий — 2000 мин/мес, каждая задача оплачивается минимум минутой.
  Не добавляй запусков на каждый push/метку; пропуск — через `if:` у задачи (пропущенная не оплачивается).
- **Нет `opened` в триггерах `ci.yml`** (2026-11-19): PR, открытый ботом, давал прогон `action_required`, который после мержа становился красным без задач. PR собирается на `ready_for_review` и push.
- `auto-pr.yml` — draft PR на push, создающий агентскую ветку (CI не зовёт); `automerge.yml` — мерж в `dev` после зелёного CI
  (логика — `scripts/ci/automerge.sh`); `release.yml` — кнопка релиза (описание — `scripts/release_notes.py`).
- Автомерж зовут трое: `ready_for_review`/метки (`automerge.yml`), `workflow_run` и **последний шаг зелёного CI ветки**
  (`CI_GREEN_SHA`). Прогон CI, запущенный ботом (dispatch), `workflow_run` не порождает — без шага
  PR, снятый с черновика до конца CI, висел (#223, #229).
- Мерж/PR через `GITHUB_TOKEN` **не запускает** `push`/`pull_request`-workflow — поэтому они вызывают
  `gh workflow run ci.yml` (dispatch разрешён). `workflow_run` и кнопки работают из копии в `main`: правка
  `automerge.sh`/`automerge.yml`/`release.yml` действует после релиза.

## Что где проверяется
| Где | Что | Время (11.2026) |
|---|---|---|
| PR в `dev`, голова с `Agent-Check: full`, `dev` по коду не ушёл | только тесты скриптов: полный `check` прошёл у агента на этих файлах (`scripts/ci/agent-checked.sh`) | ~1 мин |
| PR в `dev`, иначе | тесты скриптов + `check assembleDebug` одним вызовом, debug APK в артефактах (14 дней) | ~5,5 мин |
| PR, только `docs/` и `*.md` | только тесты скриптов (шаг «Detect code changes») | <1 мин |
| `dev` после мержа | Gradle **пропускается**, если дерево merge-коммита = дереву головы PR и там CI зелёный (`scripts/ci/tree-already-checked.sh`); иначе как PR | <1 мин |
| `dev` ночью (`warm-cache.yml`, 02:23 UTC) | полный `check assembleDebug` на коммите `dev`, если он изменился; пишет кэш Gradle и ключ `nightly-dev-<sha>`; красный → задача «Ночная проверка dev упала» | ~6 мин |
| PR в `main` не из `dev` (хотфикс) | `check assembleDebug` + эмулятор параллельно, раздел `whats-new.md`; задача `hotfix` вливает | ~15 мин |
| `main` (релиз) | без lint и тестов (дерево проверено на `dev`); `assembleDebug assembleRelease` **одним** вызовом Gradle | |

- **`BUILD_NUMBER` только на `main`.** Он попадает в `versionCode` (BuildConfig, манифест); новый номер на каждом прогоне
  выбивал из кэша все задачи `:app` (88 из 144 на PR только со скриптами, run 320). APK из PR — `versionCode` 1.
- **Номер версии `VERSION_NAME`** — только на `main` (#268; `scripts/ci/version_name.py`, нужен `fetch-depth: 0`): `<major>.<minor>`.
  Каждый релиз = мерж `dev` → `main`. Мажор — `major` в `version.properties`; минор — число релизов **после** того мержа, где этот мажор
  появился: релиз с новым `major` сам становится `X.0`, дальше `X.1`, `X.2`… (еженедельный релиз тоже +1). Единственное ручное действие —
  поднять `major` в `dev` (по слову владельца) и записать пункт в `whats-new.md`; смещений считать не нужно. Хотфикс (`hotfix.md`) — тоже мерж в `main`,
  следующий минор. История `0.N` (до 1.0) считалась по старому правилу (`minorOffset`, остался как запасной путь). Локально и в PR — `0.0`.
- «Не все тесты» обеспечивает build cache: задачи неизменённых модулей приходят FROM-CACHE (кэш пишут `main` и `dev`,
  PR стартуют с тёплым). Делить `check` на группы вручную не нужно — Gradle и так гонит модули параллельно.
- Release unit-тесты не запускаются (`check` берёт только debug), lintVital выключен (`lint.checkReleaseBuilds = false`).
- Скриншот-тесты дизайн-системы сравниваются в обычном `check` (`build-and-test.md` §«Скриншот-тесты»).

## Дубли и отмена
- `concurrency: ci-<ветка>` (`head_ref || ref_name`): dispatch из `auto-pr.yml` и `pull_request` того же коммита — одна
  группа, новый прогон отменяет старый. Раньше группы были `refs/heads/…` и `refs/pull/N/merge` и шли параллельно.
- `automerge.sh` и `release.yml` считают коммит зелёным, если **есть** успешный прогон (отменённые и пустые дубли не мешают).

## Правила Firebase
- Изменение `firebase/{firestore.rules,database.rules.json,firebase.json,rules-test/}` или `scripts/ci/deploy-rules.sh`
  (`scripts/ci/rules-changed.sh`): в PR — `scripts/test-rules.sh` (эмулятор, до шага автомержа), на `dev` после мержа —
  тесты и `scripts/ci/deploy-rules.sh` (секрет `FIREBASE_SERVICE_ACCOUNT`). Firestore обязателен, RTDB — warning, если базы нет.
- Отдельный workflow не годится: мерж через `GITHUB_TOKEN` не запускает `push`. Два мержа подряд отменяют прогон
  первого (concurrency) — его правила не опубликуются; перезапустить упавший/отменённый прогон на `dev` (Re-run).
  Владельцу в консоль ходить не нужно; ручной путь — `docs/setup/sync.md` §4.

## Кэши и секреты
- `warm-cache.yml` — «Ночная проверка dev» (сеть безопасности для `Agent-Check`, 2026-11-19): раз в сутки, пропуск, если коммит `dev` уже проверен
  (`scripts/ci/nightly-green.sh` ищет ключ кэша). Релиз (`release.yml`) ждёт её зелёной на коммите `dev`, нет — запускает и ждёт ~6 мин.
- `android-all` для Robolectric кэшируется отдельно (`~/.m2/repository/org/robolectric`, `actions/cache`).
- Необязательный секрет `GRADLE_ENCRYPTION_KEY` (`openssl rand -base64 16`) включает сохранение configuration cache.

## Эмулятор и еженедельный релиз (с 2026-12-01)
- `release.yml` по понедельникам (05:17 UTC) сам выпускает всё накопившееся в `dev`; **пропускается**, если новых коммитов нет
  или изменились только `docs/`, `*.md`, `scripts/agent/` (`scripts/ci/release_needed.py`, тест рядом). До 1 декабря расписание ничего не делает.
  Кнопка (Run workflow) работает как раньше; «Без проверки в эмуляторе» — для срочного выпуска.
- Перед слиянием `emulator.yml` собирает **R8 release** с x86_64 (`-PemulatorAbi=x86_64`, ключ debug) и гоняет
  `scripts/ci/emulator-smoke.sh` на эмуляторе API 34 (AVD со снимком в `actions/cache`, ключ `avd-…-vN` — поднять при смене опций): холодный старт, 4 вкладки, ночная тема на лету, шрифт 2.0, monkey 1500 событий,
  память, установка поверх. Упал — релиз не идёт. На PR не запускается (~15 мин); вручную — Actions → «Эмулятор».
- Не покрыто эмулятором (остаётся владельцу в #220, неделя тишины = «ок»): ощущения (вибрация, плавность 120 Гц), синк двух телефонов,
  установка поверх прошлого релиза (он только ARM), уведомления о платежах.

## Релизы и отчёты
- На push в `main` — GitHub Release `build-<N>` с `co-shell-debug.apk` (и `co-shell.apk`, если включено
  самообновление); последняя — `https://github.com/winerar/co-shell/releases/latest` (репозиторий приватный).
- Упавший `check` пишет короткую сводку (`scripts/agent/build-summary.sh --ci`) в summary джоба и одним
  комментарием `<!-- ci-summary -->` в PR (обновляется; после зелёного — «исправлено»).
- `aibench.yml` — только вручную (Actions → «Замер моделей»): собирает `tools/aibench` и кладёт APK пре-релизом `aibench-N`; в CI приложения и в релиз не входит. Запускается из копии в `main` (после релиза).
- `ai-addon.yml` — только вручную: собирает `ai-addon` (необязательное дополнение «ИИ на телефоне», #587) и кладёт APK пре-релизом `ai-addon-N`; debug-подпись общим ключом — работает с debug-приложением. В CI приложения и в релиз не входит; release-дополнение для загрузки из приложения — следующий шаг #587.
- `ai-addon-release.yml` — только вручную (нужны секреты релиза): собирает `ai-addon` **release-ключом приложения** (подпись должна совпадать — разрешение привязки уровня подписи) и публикует в `co-shell-releases` под фиксированным тегом `ai-addon` (пре-релиз, `--latest=false`: `releases/latest` приложения не должен указывать на дополнение) файлы `version.json` + APK; оттуда шаг 1 экрана «ИИ на телефоне» скачивает дополнение. Как любой новый workflow — работает из копии в `main`.
